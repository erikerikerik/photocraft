# Milestone 1 bug hunt (Oct 14, evening)

Two independent reviewers (Claude subagents that had not seen the work being built) read all M1 code: one the PhotoCraft side (`crates/engine` AI parts, `crates/ai-client`, app wiring; reading only), one Craft AI Manager (all of `crates/caim`; confirmed several findings by running). Claude checked the top finding (double blend) by reading both sides. Fixes: **BF-01** (CAIM) and **BF-02** (PhotoCraft) in `agents/TASKS.md`. Contract decision: SPEC amendment 16.

## Both sides

| # | Severity | Finding | Fix |
|---|---|---|---|
| X1 | wrong output | **Soft selections blended twice.** CAIM blends its fill by mask coverage (`lama.rs` `blend`, `backend.rs` fake) and PhotoCraft gives the layer alpha = coverage again (`edit_menu_cmds.rs` ~583). 50% coverage → 25% fill; feathered edges look hard. Tests miss it because `FakeProvider` blends too. | Amendment 16: CAIM returns full-strength fill where mask > 0; PhotoCraft blends. Update both fakes and add a test with a 50% mask that expects 50%. |
| X2 | bad UX | **Early error replies (401 / Host 400 / 413 / 503) arrive as "lost the connection".** CAIM answers after the headers and closes with the body unread; the client writes the whole body before reading, gets EPIPE after ~4 MB (confirmed). The common case is CAIM restarted with a new token. | CAIM: after an early error, `shutdown(Write)` then drain the body (bounded by Content-Length and time). Client: if the write fails, still try to read and use a parsed status. |

## Craft AI Manager (BF-01)

| # | Severity | Finding (confirmed by running unless noted) | Fix |
|---|---|---|---|
| C1 | security (local DoS) | **Slowloris lockout without the token:** 16 connections sending one byte every 20 s keep all slots; the 30 s timeout is per read and the token is checked only after the full head. PhotoCraft gets 503 indefinitely. | One overall deadline per request (head within ~5 s; body against a total budget), tracked across reads. |
| C2 | wrong output | **Thin selections vanish when the crop is downscaled:** `mask_plane` samples one source pixel per model pixel, so a 1–2 px stroke (wires, power lines) sums to 0 at 512. LaMa gets no hole. | When shrinking, a model pixel is covered if any source pixel in its area is (max-pool); sampling only when enlarging. |
| C3 | memory leak | **Cancelling a queued job keeps its input forever:** `run_one` returns early without clearing `input` or setting `finished_at`, so the sweep never removes it (up to ~512 MB per job). | In `cancel()` for a queued job, set `finished_at` and drop `input` (or in `run_one`'s early return). |
| C4 | bad UX | **Cancelled job shows a stale stage message** ("…preparing the image.", progress 0.2). | Ignore progress after cancel, or set the message to "Cancelled." in `finish()`. |
| C5 | quality | **Wide/tall selections get a squashed crop** when a squarer one fits (400×20 box in 2000×300 → 600×160 instead of 600×300). | Clamp each side separately: `w = min(side, W)`, `h = min(side, H)`, then centre. |
| C6 | wrong output (by reading) | **Two installs at once can leave a corrupt file marked verified** (shared `.part`, `File::create` truncates). | Create `.part` exclusively (or per-process name / lock file) and `sync_all` before rename. |
| C7 | robustness (by reading) | Any accept error other than WouldBlock/Interrupted ends the accept loop (e.g. `ConnectionAborted`, `WSAECONNRESET`). | Keep serving on per-connection accept errors. |
| C8 | robustness (by reading) | If sending to the worker fails, the job stays `Queued` and the 500 says "has no job with that id". Only after the worker stopped. | Remove the entry and answer with the right sentence. |

Checked and correct (CAIM): token-first constant-time check, Host check, atomic 0600 endpoint file, job-id charset, request framing caps, multipart order (the truncation claim is corrected by BF-03 below), PNG limits **before** decode (no decompression bomb), LaMa geometry incl. edges and tiny images, mask==0 bit-for-bit, failed model load → failed job (worker survives), cancel during run (ORT terminate), 503 at 8, 10-min expiry, download hash/size, no panic paths.

## PhotoCraft (BF-02)

| # | Severity | Finding (confirmed by reading) | Fix |
|---|---|---|---|
| P1 | wrong output / bad UX | **The window sent is Content-Aware Fill's sampling window** (square of 4·√area), not a crop around the selection. On a 96 MP image a ≥2000² selection exceeds 64 MP; the user waits for a >1 GB encode/upload, then gets "over 64 megapixels". | Send the selection bbox + padding (amendment 16); refuse > `max_pixels` before reading pixels. |
| P2 | bad UX | `/v1/tasks` `max_pixels` is never read. | Check it (or 64 MP) in `generative_cmds::run` before the job starts. |
| P3 | bad UX | **A failed poll/result leaves the job running on CAIM**; repeated failures fill CAIM's queue (→ 503). One transient poll error fails the whole job. | DELETE on every error after submit; tolerate 1–2 poll errors. |
| P4 | bad UX | **"Manager isn't running" only after encoding** the image (seconds and hundreds of MB on a big window). | Load `endpoint.json` first, then encode. |
| P5 | crash risk (OOM) | **Several full copies of the request in memory** (f32 window, samples, PNG, multipart body, another copy in `write_request`): ~2.5 GB peak for a 36 MP 16-bit RGBA window; total body never checked against 1 GiB. | Write head and parts separately (no concatenation); check the total. |
| P6 | spec gap | 32-bit documents: amendment 4 asks for "clamped, with a note in the result"; no note is added. | Add the note to the command result. (Linear EXR data sent unconverted: noted, no change in M1.) |
| P7 | nits | Progress jumps back 0.1 → 0; `failed` with empty message → error with no text; 401 message lacks a full stop; non-boolean `sampleAllLayers` silently false; PNG default compression (use fast on loopback). | Small fixes. |

Checked and correct (PhotoCraft): amendment 11 headers and multipart order, job JSON fields, f32→int conversion, 16-bit big-endian, result validation, endpoint paths and override, token never logged, reply caps, 401 mapping, network off the UI thread, document locked during the job, result discarded if the document changed, one-step undo onto "Generative Fill", cancel leaves the document unchanged, empty / off-canvas / 1-px selections, unsupported colour modes refused, provider wired in app, CLI and MCP.

## BF-03 (Codex)

Follow-up to BF-01, CAIM [PR #2](https://github.com/erikerikerik/craft-ai-manager/pull/2), branch `ai/bf-03-caim-resource-recovery`. This corrects the earlier "multipart truncation: correct" assessment: a boundary prefix inside PNG bytes was mistaken for a delimiter. The initial BF-03 review also found two blockers; the follow-up adds allocation-order guards and restores the SPEC amendment 11 64 MP contract without changing `max_pixels`.

| Finding | Fix / regression evidence |
|---|---|
| Extreme aspect-ratio resize/mask intermediates could be hundreds of MB | Execute the smaller axis first; tests cap the actual intermediate at 512 elements for 1×200,000 / 200,000×1 cases. Forcing the old order fails before allocating 102,400,000 elements; neither test relies on wall-clock alone. Growing RGB axes compute weights on demand rather than allocating a weight vector per output pixel. |
| Aggregate image memory / retained records were unbounded | Shared 2 GiB image-data budget, roughly 32 B/pixel plus 32 MiB working overhead; an upload's body charge is atomically replaced with its peak charge so normal PNG bytes are not double-counted. Extra-large encoded parts include a separate decode-phase bound. 8000×8000 RGBA16 passes idle admission; the same request gets 503 only during contention and fits again after release. A request exceeding the entire budget gets 413. The advertised 64 MP ceiling remains unchanged. Tests also cover the 1,024-record cap and expiry. |
| Socket response writes and shutdown could hang | Whole-response write deadline, cancellation-aware socket reads/writes (100 ms polling for Windows), separate headers/body, no second response after a partial write failure. |
| Shutdown left running/queued jobs active | Close admission, signal active cancellation, free queued input; already-admitted uploads cannot enqueue after stop. |
| A failed PNG transfer discarded the only result | Delivery guard restores the PNG and its reservation on detected failure; successful writes still consume it. A concurrent transfer gets 409. No new acknowledgement protocol is claimed. |
| Multipart delimiter prefixes caused truncation | Require a valid suffix; accept RFC 2046 space/tab transport padding on opening, intermediate, and closing boundary lines. Binary-prefix and padding regressions cover both cases. |
| Missing defensive regressions / API bypass | Test `leftover.len() > Content-Length` → 400 before reading; make `take_png` private and test-only so production goes through the transfer guard. |

CAIM receipt records exact validation results and remaining limitations. ORT session memory, allocator overhead, and kernel buffers remain outside the image-data accounting. The two budget/order blockers must be independently re-reviewed on the follow-up commit, with CI green, before PR #2 leaves draft. PhotoCraft BF-02 and its `/v1/tasks` fallback remain separate work.
