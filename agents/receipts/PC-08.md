# `crates/engine/src/ai.rs` - the protocol types (backend-neutral, wasm-safe)

- `AiTask::SubjectMask` (`"subject_mask"`), next to `FillMaskedArea`.
- `AiOutput::Image { pixels, format }` and `AiOutput::Mask { coverage, size }` replace the flat `pixels`/`format` fields of `AiResult`. A mask is one finite value in 0..=1 per pixel, row-major, at the size the provider received. Every Generative Fill call site now reads `AiOutput::Image`; no Fill behaviour changed.
- `AiRequest.sent_size: Option<Size>` with `sent_image_size()` (amendment 18): the size actually sent, which is the window size when it is `None`. `AiRequest::validate()` now checks the pixel and coverage buffers against `sent_image_size()` rather than the window, which is what makes a downscaled mask request legal; a fill request is unaffected because it sends `None`.
- `AiProvenance { model_version, model_sha256, device_requested, device_name, fallback_reason, diagnostics, load_ms, run_ms }`, every field optional and `#[serde(default)]`. Missing means unknown, never an error. `AiResult.device` keeps its old meaning (the backend that ran).
- `AiResult::check_against(&AiRequest)` accepts an `Image` as before and, for a `Mask`, requires the size to equal `sent_image_size()` and every value to be finite and in 0..=1. `run_to_completion` cancels the job on the provider when validation fails, as it already did for a bad image.
- `From<AiError> for EngineError`: `Cancelled` stays `EngineError::Cancelled`, everything else becomes `EngineError::Other` with the provider sentence, so `AiError::NoProvider` reaches the user as exactly "Craft AI Manager isn't running".

# `crates/engine/src/ai_segment_cmds.rs` (new) - the shared AI path

- `method(&Value, cmd)` reads the param: missing or `null` is `classical`; anything else is `EngineError::BadParams` naming `"classical"` and `"ai"`.
- `mask_job` is the whole protocol: ask `max_pixels(SubjectMask)` (falling back to `DEFAULT_MAX_PIXELS`), require `tasks()` to contain `SubjectMask` - otherwise the exact sentence "The Select Subject model isn't installed. Open Craft AI Manager to add it." - choose the sent size, read the image, submit, `run_to_completion` with a 100 ms poll, and stretch the mask back. A mask task is never refused for its size.
- `sent_size` keeps the aspect ratio and takes the largest size whose area fits the limit; `read_scaled` averages source areas in 256-row strips (rayon off `wasm32`) so a full-resolution canvas is never held in memory at once, and asks the job's cancel flag between strips; `coverage_bbox` and `touched_rect` work out which document pixels the mask can reach, and `upscale_bilinear` builds only that sub-rect with the edge clamped, refusing one over `MAX_MASK_PIXELS` before allocating; `mask_region` quantises to 8-bit coverage over the bounding box of the pixels it touches, which is the `Region` shape both classical commands already apply.
- `select_subject` runs in `jobs::run` (label "Select Subject", document locked) and applies the result through `smartselect_cmds::apply`, so `mode` replace/add/subtract/intersect and the one-step history are the classical command's own code. `sampleAllLayers` keeps the classical default of `true`.
- `remove_background` runs in `jobs::edit_job` and reuses `cutout_cmds::check` (unlocked pixel layer), `cutout_cmds::REFINE`, `extra_cmds::background_to_layer_for_mask` and `matting::region_surface`, in the same order as the classical command. `refine` defaults to `false` for `ai` (amendment 18: the model's matte is already soft), and the layer's pixels are never touched. `sampleAllLayers` keeps the classical default of `false`.
- Both results carry an `ai` object with the Generative Fill names (`model`, `device`, `provider`, `elapsedMs`) plus the new provenance fields; a field the provider did not report is left out.

# Things found on the way

- `upscale_bilinear` blended the last row and column with zero instead of with the edge value, which would have darkened the border of every AI selection. Both sample indices are clamped now, and `the_upscaled_mask_blends_with_the_edge_not_with_zero` pins it.
- `AiRequest::validate()` checked the buffers against `window`, so a mask request sent at a downscaled size would have been rejected by the provider contract. It checks `sent_image_size()` now.
- The branch broke `cargo test -p photocraft-automation` by dropping `AiJobState` from an import; the workspace clippy run caught it, which is why the gate list here includes the workspace run and not only the two touched crates.

# Review rounds

- Round 1: `@codex review` on the draft PR, reviewed commit `459019eb` (2026-10-17 18:30Z). Two P2s, both in `crates/engine/src/ai_segment_cmds.rs`. Both are real, and both are fixed in the commit after this receipt:
  - `sent_size` (line 101) could return a size over the limit when one dimension had already reached one pixel: `Size::new(1200, 1)` under 600 sent 1200x1, which is 1,200 pixels. The loop now clamps the other side once the height cannot shrink further, so a thin panorama fits under the limit instead of being rejected by the provider. Pinned by three thin-document cases added to `sent_size_keeps_the_ratio_under_the_limit`.

Strips now go out a batch at a time under a 32 MiB budget (`MAX_RESIDENT_BYTES`, new `strips_in_flight`), and `the_downscale_never_keeps_the_whole_canvas_in_memory` tests the bound directly. The results are unchanged; the 6000x4000 test still sends 1254x836.
  - Re-review asked for on the new head commit only. Gate counts moved to 18 for `--lib ai_segment` and 177 for `--lib ai` because of the two new assertions and the new test.
- Round 2: `@codex review` on `8aa781b3` (2026-10-17 18:50Z). One P1 and one P2, both in
  `crates/engine/src/ai_segment_cmds.rs`, both real, both fixed:
  - **P1** - `upscale_bilinear` stretched the mask into one `f32` for every pixel of the document
    before the `Region` was cut out of it. `file.new` allows 300,000x300,000, so a document the
    engine accepts could ask for 360 GB and abort the process instead of returning an error. The
    upscale now builds only the document pixels the mask can touch: `coverage_bbox` finds the box
    in the provider's own answer (never more than `max_pixels`), `touched_rect` inverts the
    bilinear map to the document pixels that can reach it, and `MAX_MASK_PIXELS` - the same
    64 megapixel budget the AI path already works to - refuses before allocating, in the words the
    other size limits use. `cropping_the_upscale_does_not_change_the_region` pins that the crop
    changes nothing: outside the box the full upscale is zero, and the Region is byte for byte the
    same.
  - **P2** - the strip budget counted four bytes a source pixel when `Sampler::rgba` answers
    `[f32; 4]`, so it under-estimated every strip by four. It counts sixteen now, and
    `MAX_RESIDENT_BYTES` moved to 64 MiB so a 6000x4000 canvas still keeps two strips in flight
    (about 30 MB each) rather than one. The wasm path batches the same way, which also clears the
    unused-variable warning the round 1 fix left there.
  - Gate counts moved to 20 for `--lib ai_segment` and 179 for `--lib ai`. This is the second of
    the two fix rounds the mandate allows, so PR #24 now waits on an approval rather than on a
