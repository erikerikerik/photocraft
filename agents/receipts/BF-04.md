### `crates/ai-client/src/endpoint.rs`

- `read_file` stats the path first and refuses anything that is not a regular file **before opening it**, then judges **the handle it opened** as well (`file.metadata()`), which is upstream's pattern for the mode and size checks: they describe the bytes actually read. The pre-check exists because `File::open` on a fifo with no writer blocks forever (review round 2 below).
- `!meta.is_file()` -> `AiError::NoProvider`, the same answer as for every other unusable file, so a folder, a fifo, a device or a symlink to something odd still reads to the user as "Craft AI Manager isn't running".
- `#[cfg(unix)]` with `std::os::unix::fs::MetadataExt`: `meta.mode() & 0o077 != 0` -> `AiError::Other` with one sentence: `Craft AI Manager's endpoint file can be read or changed by other users (mode <octal>), so PhotoCraft won't use it. Restart Craft AI Manager to write a fresh one.` The octal is the low nine bits, so the user sees `644` rather than `100644`.
- Windows is left as it was, with a comment saying why: the file lives in this user's own `%LOCALAPPDATA%`, where those mode bits say nothing about who can read it. `#[cfg(unix)]` keeps the check out of the Windows build entirely.
- The `load` doc comment gained one paragraph, so the rule is visible where the function is described.

## Review round 2: Codex-cloud's P2 - the open blocks before the check (our finding, fixed)

Codex-cloud reviewed `a0002f5` and left one P2 inline comment (`crates/ai-client/src/endpoint.rs:101`, 2026-10-18T09:31Z): on Unix, when the endpoint path is a **fifo with no writer**, `File::open` blocks until a writer appears, so the `is_file()` check added in round 1 can never run and the AI job worker sits in the open forever. Correct, and it is our bug: the prompt asked for the check on the open handle, and I put every check after the open.

The fix is the second option the finding offers - "reject special files without performing a blocking open":

- `read_file` now does `std::fs::metadata(path)` (a stat: it opens nothing) and returns `AiError::NoProvider` unless the path is a regular file, **before** `File::open`. A fifo, socket, device or folder is refused without ever being opened, so nothing can block.
- The handle check stays. It is what makes the mode and size checks describe the file whose bytes we read, which is the point of the prompt's "check the opened file's metadata, not the path".
- `std::fs::metadata` follows a symlink, so the symlink behaviour the round-1 receipt documented is unchanged: a symlink to a `0600` regular file still loads.
- Regression test the finding asked for: `an_endpoint_fifo_with_no_writer_is_refused_without_opening_it`. It makes a real fifo with no peer, calls `read_file` on a worker thread, and fails after five seconds if the answer does not arrive - so a regression shows up as a red test, not as a hung CI job. It is not `#[cfg(unix)]` so Windows compiles it (it prints a skip line there: no `mkfifo`), and it runs for real on ubuntu and FreeBSD.
- **Residual, stated plainly:** a file swapped in *between* the stat and the open could still be a fifo, and closing that needs `O_NONBLOCK` on the open - `std` only offers it through `OpenOptionsExt::custom_flags` with a per-platform constant, i.e. a magic number per OS for a race that needs an attacker watching the directory in a sub-millisecond window. The realistic case (a fifo already sitting where `endpoint.json` belongs) is now refused without opening. Noted here rather than papered over.
