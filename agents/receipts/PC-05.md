## What landed

One file, no product code, no new dependencies: `crates/automation/tests/generative_fill.rs` (261 lines).
It drives the real MCP server (`PhotocraftMcp::with_backend(Backend::Headless(..))`) over an in-memory
`tokio::io::duplex` stream with the `rmcp` client the crate's other tests already use, and calls only
tools that exist: `doc_new`, `command_run`, `jobs_list`, `jobs_cancel`, `doc_inspect`, `doc_render_preview`.

`photocraft-engine`'s own `FakeProvider` is private to that crate, so the file carries its own stand-in
`FakeFill` (SPEC amendment 16: inside the mask the fill comes back at full strength; outside it the input
is returned bit for bit). It either finishes after two polls or stays `Running` forever, which is how the
cancel test gets a provider that is genuinely still working. The provider goes in through
`Headless::session.set_ai_provider(..)`, the seam PC-04's receipt pointed at; `photocraft-automation`'s
manifest is untouched.

**Test 1 - `generative_fill_over_mcp_adds_a_layer_and_one_undo_removes_it`.** A 64x48 RGB document with a
`select.rect` selection. `command_run {"id": "edit.generativeFill", "wait": false}` returns a job id; the
job's `jobs.list` entry is `state: running`, `label: "Generative Fill"` (decision D1),
`command: edit.generativeFill`. When it settles: `state: done`, `result.filled > 0`, `result.ai.model` is
`solid-fill` and `result.ai.provider` is `local fake` (B08: the provenance travels with the job), and
`result.layer` names the new layer. `doc_inspect` goes from `["Background"]` to
`["Generative Fill", "Background"]`, the old layer's entry is exactly what it was, and `doc_render_preview`
changes. One `edit.undo` puts the layer list, the whole layer tree and the rendered PNG back as they were.

**Test 2 - `cancelling_a_generative_fill_over_mcp_leaves_the_document_unchanged`.** The fake never
finishes. The test waits on the provider's poll counter so it cancels a fill that is really running, then
`jobs_cancel {"job": N}` returns `{"cancelled": 1}`, the job settles as `state: cancelled`, the fake saw
exactly one `cancel` call, and the layer tree and the rendered PNG are identical to before - not one pixel
moved.

## Review

- **Round 1 - Codex-cloud on `24048aa` (2026-10-16), one finding (P2).** The fill test read
  `jobs.list` right after `command_run` and asserted `state == "running"`; a ~200 ms deschedule lets
  the fake reach its third poll first, and `jobs.list` would legitimately report `done`. Fixed by
  gating the fake: `FakeFill` has a `hold` flag, every poll stays `Running` while it is set, and the
  test clears it after the three running-state assertions, so the job settles on the next poll. What
  the test proves is unchanged.

## Known gaps and follow-ups

- The provider still goes in through `Backend::Headless`, so `photocraft-automation` stays free of
  `photocraft-ai-client`. The real manager over MCP is covered by PC-06 in the desktop app, not by an
  automated test; an MCP test against a live `caim serve` would need a port and a token, and belongs with
  the CI work.
- `jobs_list` is polled, not pushed, so the tests wait on the fake's counters rather than on a timer.
- The cancel test asserts the provider got exactly one `cancel` call; it does not assert that the manager
  deleted the job (PC-03's client tests and CAIM's `protocol.rs` cover that side).
