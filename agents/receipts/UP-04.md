**The bug** (`crates/ipp/src/lib.rs:143`, verbatim from `v0.10.0`): the TCP arm of `Endpoint::connect`
did

```rust
let addr = (host.as_str(), *port).to_socket_addrs().map_err(...)?.next();
```

so only the **first** address the resolver returned was ever tried. A print-server name that resolves
to several addresses - dual-stack, multihomed, a CUPS host with more than one interface - fails as soon
as the first answer is not the one serving CUPS: `reachable()` reports no server, a server named in
`CUPS_SERVER` fails, and `detect()` falls back to its built-in candidates even though a working
endpoint exists.

**The fix**: walk every resolved address and return the first successful connect. The last error is
kept for the `Unreachable` message, so a name where nothing listens still reports
`host:port: <refusal>`, and a name that resolves to nothing still reports `no address`. The
`connect_timeout` budget (`CONNECT`, 3 s) is per address, as before.

**Body:**

```
`Endpoint::connect` in `crates/ipp/src/lib.rs` resolves the print-server name and keeps only the first
address: `to_socket_addrs()?.next()`. On a dual-stack or multihomed machine a print-server name
resolves to several addresses, and if the first one is not the one serving CUPS the client gives up:
`reachable()` reports no server, a server named in `CUPS_SERVER` fails, and `detect()` falls back to
its built-in candidates even though a working endpoint exists.

Reproduce it without a printer: listen on `127.0.0.1` only, then ask for `Endpoint::Tcp("localhost",
that_port).reachable()`. On this Windows box `localhost` resolves to `::1` first, so the client tries
`[::1]:port`, is refused, and reports no print server - even though the IPv4 answer is serving.

Fix: walk every resolved address and return the first successful connect. The last error is kept for
the `Unreachable` message, and a name that resolves to nothing still reports `no address`. The
`connect_timeout` budget is per address, as before.

Tests: `every_resolved_address_is_tried_and_the_first_that_opens_wins` hands the loop two addresses of
its own - the first closed, the second listening - so it needs no host configuration, and it also
checks that a server where nothing listens reports the last error and that an empty address list still
says `no address`. `a_server_name_that_resolves_to_several_addresses_is_tried_at_each_one` does the same
end to end over `Endpoint::Tcp("localhost", port)`: it leaves the first resolved answer closed and
listens on every later one, so the first attempt is refused and only a later address can open. It was
red before the change (`[::1]:64713 is closed but 127.0.0.1:64713 serves the port`) and is green after,
and it prints a skip line rather than failing on a host whose `localhost` has a single answer.

Gates: `cargo test -p photocraft-ipp` 11 passed / 0 failed; `cargo clippy -p photocraft-ipp
--all-targets -- -D warnings` clean; `cargo xtask layers` OK; `cargo fmt` clean.

Found while syncing our fork onto v0.10.0. Credit for the code this touches: @diegochagas, `235e7578`
(#3017).
```

## Review round 1 (Codex-cloud on #56)

- Codex-cloud answered `COMMENTED` with one inline **P2** at `crates/ipp/src/tests.rs:204`: the test
  asserted `addrs.len() > 1`, which is a property of the machine, not of the code. On an IPv4-only,
  IPv6-disabled or minimally configured host `localhost` legitimately resolves to one address, so the
  test would fail there while the connection logic is correct. It asked for a controlled
  resolver/connector seam instead.
- It is right, and it is the kind of thing an upstream maintainer would ask for too. Fixed in `829538f0`
  (upstream `ce9b2542`): the loop moved out of the match arm into `connect_tcp(host, port, addrs)`,
  which the TCP arm hands the whole resolved list, and the test now passes two addresses of its own -
  first closed, second listening - so it needs no host configuration at all. That test also covers the
  other two exits: nothing listening anywhere keeps the **last** error, and an empty list still answers
  `no address`.
- The end-to-end test over `Endpoint::Tcp("localhost", port)` stays, because it is the one that proves
  `connect` really hands over the whole list; where the host has a single answer it prints
  "localhost resolves to one address ([..]) here: nothing to try, the seam test covers this" and returns
  instead of failing.
- **Sensitivity, re-proved after the change:** with the call site put back to one address
  (`connect_tcp(host, *port, addrs.take(1))`) and nothing else touched, the end-to-end test went red
  again - `[::1]:51257 is closed but 127.0.0.1:51257 serves the port` - and the seam test stayed green.
  Restored, 11 passed / 0 failed, three runs in a row.
- The upstream PR body below is written for the two-commit head, so the test paragraph names both tests.
