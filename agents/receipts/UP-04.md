**The bug** (`crates/ipp/src/lib.rs:143`, verbatim from `v0.10.0`): the TCP arm of `Endpoint::connect`
did

```rust
let addr = (host.as_str(), *port).to_socket_addrs().map_err(...)?.next();
```

so only the **first** address the resolver returned was ever tried. A print-server name that resolves
to several addresses - dual-stack, multihomed, a CUPS host with more than one interface - fails as soon
as the first answer is not the one serving CUPS: `reachable()` reports no server, a server named in
`CUPS_SERVER` fails, and `detect()` falls back to its built-in candidates even though a working
endpoint exists.

**The fix**: walk every resolved address and return the first successful connect. The last error is
kept for the `Unreachable` message, so a name where nothing listens still reports
`host:port: <refusal>`, and a name that resolves to nothing still reports `no address`. The
`connect_timeout` budget (`CONNECT`, 3 s) is per address, as before.

**Body:**

```
`Endpoint::connect` in `crates/ipp/src/lib.rs` resolves the print-server name and keeps only the first
address: `to_socket_addrs()?.next()`. On a dual-stack or multihomed machine a print-server name
resolves to several addresses, and if the first one is not the one serving CUPS the client gives up:
`reachable()` reports no server, a server named in `CUPS_SERVER` fails, and `detect()` falls back to
its built-in candidates even though a working endpoint exists.

Reproduce it without a printer: listen on `127.0.0.1` only, then ask for `Endpoint::Tcp("localhost",
that_port).reachable()`. On this Windows box `localhost` resolves to `::1` first, so the client tries
`[::1]:port`, is refused, and reports no print server - even though the IPv4 answer is serving.

Fix: walk every resolved address and return the first successful connect. The last error is kept for
the `Unreachable` message, and a name that resolves to nothing still reports `no address`. The
`connect_timeout` budget is per address, as before.

Tests: `connect_tcp(host, port, addrs, open)` takes the resolved list and the connect call, so
`every_resolved_address_is_tried_and_the_first_that_opens_wins` can hand it two addresses of its own and
answer for them: it refuses the first (an RFC 5737 documentation address), really connects to the second
(a listener it holds open), and asserts the order it was asked for. The same test shows that the last
error wins - the two attempts fail with different messages - and that an empty address list still says
`no address`. No part of it needs a free port. `a_server_name_that_resolves_to_several_addresses_is_tried_at_each_one`
does it end to end over `Endpoint::Tcp("localhost", port)`: it leaves the first resolved answer closed
and listens on every later one, so the first attempt is refused and only a later address can open. It was
red before the change (`[::1]:64713 is closed but 127.0.0.1:64713 serves the port`) and is green after;
it prints a skip line on a host whose `localhost` has a single answer.

Gates: `cargo test -p photocraft-ipp` 11 passed / 0 failed; `cargo clippy -p photocraft-ipp
--all-targets -- -D warnings` clean; `cargo xtask layers` OK; `cargo fmt` clean.

Found while syncing our fork onto v0.10.0. Credit for the code this touches: @diegochagas, `235e7578`
(#3017).
```

## Review round 1 (Codex-cloud on #56)

- Codex-cloud answered `COMMENTED` with one inline **P2** at `crates/ipp/src/tests.rs:204`: the test
  asserted `addrs.len() > 1`, which is a property of the machine, not of the code. On an IPv4-only,
  IPv6-disabled or minimally configured host `localhost` legitimately resolves to one address, so the
  test would fail there while the connection logic is correct. It asked for a controlled
  resolver/connector seam instead.
- It is right, and it is the kind of thing an upstream maintainer would ask for too. Fixed in `829538f0`
  (upstream `ce9b2542`): the loop moved out of the match arm into `connect_tcp(host, port, addrs)`,
  which the TCP arm hands the whole resolved list, and the test now passes two addresses of its own -
  first closed, second listening - so it needs no host configuration at all. That test also covers the
  other two exits: nothing listening anywhere keeps the **last** error, and an empty list still answers
  `no address`.
- The end-to-end test over `Endpoint::Tcp("localhost", port)` stays, because it is the one that proves
  `connect` really hands over the whole list; where the host has a single answer it prints
  "localhost resolves to one address ([..]) here: nothing to try, the seam test covers this" and returns
  instead of failing.
- **Sensitivity, re-proved after the change:** with the call site put back to one address
  (`connect_tcp(host, *port, addrs.take(1))`) and nothing else touched, the end-to-end test went red

  Restored, 11 passed / 0 failed, three runs in a row.

## Review round 2 (Codex-cloud on #56)

- Codex-cloud reviewed `5ad781de` (review 5566266580, 2026-10-19 02:13:58Z) and came back with two more
  **P2s**, both about the seam test written in round 1. Both are right.
- **`crates/ipp/src/tests.rs:202` (4309799853), "Avoid recycling an ephemeral port for the live
  listener".** The closed address came from a `127.0.0.1:0` bind dropped a line earlier, so on a runner
  whose ephemeral allocator hands that port straight back `serving` can equal `closed`: the later
  "nothing listening" check would connect to `live` and the test would panic, and another process could
  claim the released port and leave `live.accept()` blocked. It asked for a deterministically invalid
  endpoint or the connector injected as part of the seam.
- **`crates/ipp/src/tests.rs:211` (4309799858), "Distinguish the attempts in the last-error test".**
  `[closed, closed]` cannot show that the last error wins - both attempts fail the same way, so an
  implementation that kept the first error would pass as well, while the doc comment claims that exit is
  covered.
- **Fixed in `88116191` (upstream `d8ad20e8`), taking the injected-connector option in both cases.**
  `connect_tcp` now takes the connect call as a fourth parameter,
  `open: impl FnMut(SocketAddr) -> std::io::Result<TcpStream>`, and the TCP arm passes
  `|addr| TcpStream::connect_timeout(&addr, CONNECT)`. The seam test's fake connector records every
  address it was asked for, refuses the ones the test wants closed and really connects only to the
  listener it holds open, so no address is called closed just because a port happened to be free a
  moment ago. The fake addresses are RFC 5737 documentation addresses (`192.0.2.1:631`, `192.0.2.9:631`),
  which are never contacted for real because the connector answers for them. The last-error case now
  fails the two attempts with different messages and asserts the error names the **second** address and
  not the first; the empty-list case still answers `nowhere:631: no address`.
- **The end-to-end test keeps its real sockets** - it is the one that proves `connect` hands over the
  whole list - but it no longer assumes a free port stays free: it retries the probe/listen pair up to
  five times and prints a skip line if it cannot claim the port on every resolved address. Its "nothing
  listening after the drop" half is gone, because that is the half the finding called uncontrolled; the
  seam test covers it deterministically, and the pre-existing
  `error_statuses_and_broken_replies_are_errors` already covers a real refused connect.
- **Sensitivity, re-proved on the round-2 tree:** with the call site put back to one address
  (`connect_tcp(host, *port, addrs.take(1), ..)`) and nothing else touched, the end-to-end test went red
  again - `[::1]:56655 is closed but 127.0.0.1:56655 serves the port` - and the seam test stayed green.
  That split is the point: the seam test guards the loop, the end-to-end test guards the call site.
- **Gates after round 2:** `cargo test -p photocraft-ipp` 11 passed / 0 failed; the two new tests three
  runs each, all green with no skip line; `cargo clippy -p photocraft-ipp --all-targets -- -D warnings`
