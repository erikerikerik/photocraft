# `crates/ai-client/src/protocol.rs` - the task list and what kind of answer to expect

- `parse_tasks` now reads `ready` and `output` as well as `id` and `max_pixels`. Only an explicit `false` hides a task (`ready` missing means ready, amendment 18). A task whose `output` contradicts its id is skipped rather than trusted: `subject_mask` with `"output": "image"` is a manager bug, and offering it would hand the engine a fill it did not ask for. An `output` that is missing or not a string says nothing, so an M1 list still works. Unknown ids stay skipped, and the dedup is unchanged.
- `output_of(task)` is the one place that knows which id produces which shape, so the list check and the result check cannot drift apart.
- `result_kind(kind, task)` decides what the answer must be from **the task we submitted**, then checks what the manager claims it sent. A fill accepts `"kind": "image"` or no `kind` at all (amendment 11's answer has no such field). A mask task needs `"kind": "mask"`; without it the sentence is that the manager "did not say what kind of result it sent", because guessing would mean deciding the shape of a document edit from a coin flip.
- `parse_provenance` gained `kind` (kept as text; `result_kind` interprets it) and the eight amendment 18 fields - `model_version`, `model_sha256`, `device_requested`, `device_name`, `fallback_reason`, `diagnostics`, `load_ms`, `run_ms` - returned as `extra: AiProvenance`, PC-08's type. Each is optional; a value that is `null`, empty, or of the wrong JSON type becomes `None` rather than an error, and `fallback_reason` stays free text (amendment 18 lists the values it knows but does not close the list).
- `model` in the task list is deliberately **not** read. Nothing in this crate can use it: the model that ran already arrives in every result, and the "not installed" case is the 400's own sentence (below). An accessor that returns a string nothing calls would be a second source of truth for the same fact.

# `crates/ai-client/src/pixels.rs` - reading a mask PNG

- `decode_mask(png, width, height)`: 8-bit grayscale at the size that was sent, nothing else. It refuses a PNG whose header colour type or bit depth is not 8-bit grey, refuses one whose decoded `output_color_type` disagrees with the header, and refuses one whose `output_buffer_size` is not `width * height` before allocating, then maps 0-255 to 0.0-1.0 through the same `to_floats` the fill path uses. A wrong-size, RGB or 16-bit answer is an error with words; there is no unwrap on this path.
- `mask_body_cap(width, height)`: the byte cap for a mask `result.png`, next to `result_body_cap` for images. A mask is one byte a pixel, so its cap is far smaller than an RGBA fill's; the cap is chosen before the `GET`, so a manager that answers a mask task with a huge PNG is stopped while reading, not after.

# `crates/ai-client/src/provider.rs` - the shape is decided by the job, not by the answer

- `JobRecord` now carries `task`, recorded at `submit`. That is what lets `result()` know what should come back even for a manager that never says.
- `result()` order: provenance JSON, the existing size check against the size that was sent, `result_kind`, the per-kind PNG cap, the `image/png` content type, then the decode. The fill branch is unchanged - same `decode_image`, same `record.samples` check, same `AiOutput::Image`. The mask branch returns `AiOutput::Mask { coverage, size }` at the sent size; the engine stretches it (PC-08), the client does not guess at that.
- `provenance` on the result is `provenance.extra`, so the eight new fields reach `AiResult` and the command's `ai` object. For an M1 manager they are all `None`, which the engine reports as "not said".
- Nothing else moved: no new call, no new header, no change to the multipart body, the cancel path, the endpoint-file rules or the caps that BF-01 and PC-07 fixed.

# Tests - `crates/ai-client/src/tests.rs`, nine new, 49 in all

- `an_m1_shaped_manager_answers_a_fill_exactly_as_today` (B20, first half): a task list with none of the new fields, a fill, and a result JSON with none of them. Same pixels back (within one 8-bit step, the tolerance the existing 8-bit round-trip test uses - `request()` builds values like `0.028`, which an 8-bit PNG cannot hold), and `provenance` is `AiProvenance::default()`.
- `an_m2_shaped_manager_with_unknown_fields_answers_both_tasks` (B20, second half): both tasks offered with `output`/`ready`/`model` plus fields this build has never heard of (`extra` as an object and as an array), and both a fill and a mask answered.
- `a_task_that_is_not_ready_is_not_offered`: `ready: false` hides `subject_mask` while `max_pixels` still reports its limit; an unknown id, an `output` that contradicts the id, and a repeat are all skipped; `ready: "yes"` and `"output": 3` say nothing, so the M1 answer stands.
- `a_mask_result_round_trips_at_the_sent_size`: a 5x4 mask for a 20x10 window comes back as 20 values within one 8-bit step of what was sent, all in 0..=1, and `AiResult::check_against` accepts it for the request it answers.
- `a_mask_answer_of_the_wrong_shape_is_refused`: 16-bit grey, RGB, a mask at the window's size instead of the sent size, a mask answer with no `kind`, `"kind": "image"` for a mask task, and `"kind": "mask"` for a fill - each is an `AiError::Other` with words, never a panic. The case list carries whether the client should even ask for the image, and the test asserts that: a kind decided before the fetch means no `result.png` request, so no bytes move for an answer that was already refused.
- `the_new_provenance_fields_are_parsed_or_ignored`: a full M2 result lands every field in `AiProvenance` (`fallback_reason` as text), and a result where every new field is `null`, empty, a number, an object, an array or a string-that-is-not-a-number still parses, with `extra` equal to `AiProvenance::default()`.
- `a_mask_submit_sends_the_sent_size_and_an_all_255_mask`: the same three parts in the same order; `image_size` is the sent size (40x20 for a 200x100 window at 10,20), `region` stays the whole window in document coordinates, `bit_depth` 8 and 4 channels, `provider` stays `auto` (the client never chooses a backend), the image PNG is at the sent size, and the mask PNG is 8-bit grayscale at the sent size with every byte 255.
- `a_missing_model_answers_with_its_own_sentence`: a 400 whose sentence names a missing model is passed through unchanged, and stays `AiError::Other` - it is not dressed up as a token problem.
- `select_subject_ai_gets_a_mask_through_the_real_client`: end to end through `photocraft_engine::Session` - `select.subject {"method": "ai"}` with this client and the fake manager. The queue order is the proof of the protocol: two task lists, the 202, the job state, the result JSON, the mask PNG. The command's `ai` object carries `model`, `device`, `deviceName`, `modelVersion`, `modelSha256`, `deviceRequested`, `loadMs`, `runMs`, and `fallbackReason` is absent when the manager sent `null`.

The 40 tests that were there before are unchanged and green.
