# Step 0 - the storage finding (what the prompt asks for first)

PhotoCraft already has exactly one free-form per-layer field, and the native format already saves and
loads it:

- `Layer::psd_blocks: Vec<([u8; 4], Arc<Vec<u8>>)>` - `crates/doc/src/lib.rs:641`. "Preserved
  PSD additional-layer-info blocks (key, data) for lossless round-trip of anything not modelled
  above". It is a `Vec`, not a map, and the key is the four ASCII characters a PSD tagged block has.
- The native document format carries it: `psd_blocks: Vec<(String, Hash)>` in the manifest
  (`crates/format/src/manifest.rs:227`), written per layer at `crates/format/src/convert.rs:204`
  (key hex-encoded, bytes through the blob sink) and read back at
  `crates/format/src/convert.rs:515-517`.
- A PSD keeps it: import puts every unmodelled block in there (`crates/io/src/psd_import.rs:473`),
  and export writes every block back verbatim except the keys it regenerates from fields
  (`crates/io/src/psd_export.rs:556`) - `pcai` is not one of those.
- `Layer::duplicate()` is `self.clone()` plus new ids (`crates/doc/src/lib.rs:736`), so a duplicate
  copies the record with no special code, which is what the prompt asks for.

So the record goes under one namespaced key, `pcai`, with a JSON payload. **No document-format change
was needed**, so the task row's stop-and-ask rule did not trigger: an older PhotoCraft opens such a
file and ignores the extra block (it is one more entry in a `Vec` it already round-trips), and a PSD
saved from PhotoCraft carries it as an unknown tagged block. The key is lower case, which Photoshop
never uses, so it cannot collide with a real PSD key.

Time is deliberately not stored: the prompt says to store it only where the field already has a
natural place, and a tagged block has no timestamp of its own. A record with an unknown extra key
still loads, so a later PhotoCraft can add one without breaking this one.

# `crates/engine/src/ai_provenance.rs` (new) - the shape, one write, one read

- `KEY: [u8; 4] = *b"pcai"`; `CMD_GENERATIVE_FILL = "edit.generativeFill"` and
  `CMD_REMOVE_BACKGROUND = "layer.removeBackground"`, the command ids, as the prompt asks.
- `Record { command, model, model_version?, model_sha256?, device, device_name? }`. Everything except
  the two fields every job reports is `Option` with `#[serde(default)]`: missing means unknown, never
  an error. `model_sha256` is the hash of the distributed model file (amendment 18); a runtime cache
  never appears here.
- `Record::from_result(command, &AiResult)` reads PC-08's `AiProvenance` fields plus `model` and
  `device` - it copies, it does not move, so the command result keeps carrying the same facts.
- `write(&mut Layer, &Record)` replaces the entry under our key rather than pushing a second one, so
  a layer never holds two records. `read(&Layer) -> Option<Record>` returns `None` for a layer with
  no record and also for a block under our key that does not parse - one another program wrote into
  a PSD, or a file from a newer PhotoCraft - which reads as "no record", not as an error.
- `short_sha` is the first 12 characters, or the whole value when a provider reported fewer.

# Where the record is written

- **Generative Fill** (`crates/engine/src/generative_cmds.rs`): the job closure now returns the
  `Record` next to the filled window, and `apply_content_aware_fill` writes it on the layer it
  creates, inside the same `edit_job` step that creates the layer. One undo removes the layer and the
  record together.
- `edit_menu_cmds::apply_content_aware_fill` gained one parameter, `record: Option<&Record>`. Content-Aware
  Fill, Delete and Fill pass `None`, so the classical path is unchanged and writes nothing; the
  record is written only on the `output: "new"` layer it just built, never on a layer filled in place.
- **AI Remove Background** (`crates/engine/src/ai_segment_cmds.rs`): `mask_job` takes
  `command: Option<&str>` and puts the `Record` in its `Masked` result; `remove_background` passes
  `CMD_REMOVE_BACKGROUND` and writes the record on the layer in the same statement that sets
  `layer.mask`, so undo takes the mask and the record away together and redo brings both back.
  Select Subject passes `None` - it has no layer to remember the job on.
- **Classical paths** are untouched: `method: "classical"` never reaches `mask_job`, and the
  classical Content-Aware Fill passes `None`.
- `crates/engine/src/lib.rs`: one line, `pub mod ai_provenance;`.

# Properties (U04) - `crates/ui-egui/src/ai_props_ui.rs` (new)

- `properties(ui, layer)` returns immediately when `ai_provenance::read` gives `None`, so for every
  layer that has no record the panel is pixel for pixel what it was.
- When there is one, it opens a `section(ui, "madeWith", tl!("Made with"))` - the panel's own

  `theme::ROW_GAP`) and its dim label colour, left-aligned exactly as the type panel's "Color" row paints a word label; the value is selectable text so it can be
  copied. The label is measured with `layout_no_wrap` because these are words rather than the panel's
  one- and two-character field glyphs - the same shape the type panel's "Color" row uses
  (`crates/ui-egui/src/type_tool.rs:2216`). No new styling.
- `crates/ui-egui/src/layer_props_ui.rs` gained one call, after the layer kind's sections and before
  Quick Actions, plus one sentence in the file's header comment. That is the whole upstream-file
  change.

# Things found on the way

- The i18n coverage test caught the new labels on the first run (`every_tl_literal_is_translated`
  failed with `Made with`, `SHA-256` and `Device` missing in all 20 complete catalogs). The four row
  labels would *not* have been caught, because they reach `tl!` as variables - hence the new test.
- `Layer::psd_blocks` is a `Vec`, not a map: writing twice would have left two `pcai` blocks, and
  `read` would have returned the first. `write` replaces the entry it finds, and
  `writing_again_replaces_the_record_rather_than_adding_a_second_one` pins it.
- PSD export writes our block back verbatim, so a PhotoCraft PSD opened in Photoshop 2026 carries an
  unknown `pcai` block. Photoshop ignores unknown additional-layer-info blocks, and an older
  PhotoCraft re-saves it unchanged.

## Round 1, finding 1 (P1) - an odd-length record was lost by a PSD round trip

Review comment 4309610692 on `crates/engine/src/ai_provenance.rs:88`. PSD export keeps a layer
block's pad byte **inside** the length (`crates/io/src/psd_export.rs:520-526`, the #200 rule that
keeps psd-tools aligned), so a record that serializes to an odd number of bytes comes back with a
trailing NUL, `serde_json::from_slice` calls that trailing characters, and `read` returns `None`: the
layer silently loses its "Made with" data. `sample()` serializes to 219 bytes, so **every** record
PhotoCraft writes today is odd - not an edge case.

Fix: one private `parse(data)` that drops the trailing NUL bytes before parsing (JSON never ends with
a NUL, so a pad byte cannot be part of a record) and returns `None` for an all-NUL block. `read` and
`write` both go through it.

Proof the finding was real, and that the fix is what carries it: with the trim removed,
`a_record_survives_a_psd_round_trip_whatever_its_length` fails with "a record that serialized to 219
bytes is lost by a PSD round trip" and `a_psd_pad_byte_inside_the_block_does_not_hide_the_record`
fails; with it, both pass. The round-trip test goes through `photocraft_io::export(doc, "x.psd")` and
`photocraft_io::import("x.psd", ...)`, and it asserts that its two records cover both parities, so it
cannot quietly stop covering the odd one.

## Round 1, finding 2 (P2) - a `pcai` block that is not ours was replaced

Review comment 4309610701 on `crates/engine/src/ai_provenance.rs:78`. `write` matched on the key
alone, so a PSD that came in carrying a `pcai` block we did not write lost those bytes on the next AI
command - against AGENTS.md section 8, "keep unknown PSD blocks verbatim".

Fix: `write` replaces only a block that reads back as one of our records (`parse(data).is_some()`);
anything else under the key stays byte for byte and our record goes in after it. `read` returns the
first block under the key that parses. Nothing else had to change: `psd_blocks` is a `Vec`, the
importer keeps duplicate keys (`crates/io/src/psd_import.rs:598`), export writes them back as they
came (`crates/io/src/psd_export.rs:556`), and the native format stores the list as pairs
(`crates/format/src/convert.rs:204`). Writing twice beside a foreign block still leaves exactly one
record and two blocks, which
`a_block_under_our_key_that_is_not_ours_is_kept_and_our_record_goes_beside_it` pins.

Why not a second, versioned key (the finding's other suggestion): the key is ours - lower case, which
Photoshop never uses - and a fallback key would leave a stale record behind once the foreign block
went away. The rule worth pinning is "never destroy bytes we did not write", not "never share a key".
