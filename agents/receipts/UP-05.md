**The bug** (`crates/ipp/src/lib.rs:119`, verbatim from `v0.10.0`): `Endpoint::parse` turned a server string into a host and port with

```rust
let (host, port) = server.rsplit_once(':').and_then(|(h, p)| p.parse().ok().map(|p| (h.to_string(), p))).unwrap_or((server.to_string(), 631));
```

Splitting on the **last** `:` is wrong for an IPv6 literal: `::1` becomes host `:` on port 1, and `[::1]:631` keeps its brackets inside the host, which `(host, port).to_socket_addrs()` cannot resolve on any platform. So `CUPS_SERVER=[::1]:631` - the form CUPS itself documents for an IPv6 address - is always refused by `detect()`, even when CUPS is listening there.

**The fix**, in the two address forms only:

- `[address]` or `[address]:port` takes the host from **inside** the brackets and the port from after them, so the host never carries brackets.
- A bare address with more than one `:` and no `%` is the host with the default port 631, because its last `:` cannot be told apart from a port separator.
- A zone id (`fe80::1%eth0`) carries no `:`, so a port can still follow the address.
- `host:port`, a bare host and a unix socket path (`/var/run/cups/cups.sock`) are unchanged.

## The one judgement call, for the reviewer

The prompt says to stop if scoped link-local addresses need a design decision. No decision was needed to fix the bug, but one was made about the **bare** form: a bare IPv6 literal with more than one `:` and **no** `%` keeps the default port, because there is no way to tell `fe80::1:631` apart from an address whose last group is a port. With a zone id (`fe80::1%eth0:631`) a port *is* unambiguous, so it is honoured. If upstream would rather refuse bare IPv6 literals outright, that is a one-line change in the same place; the bracketed form, which is what CUPS documents, is unaffected either way.
