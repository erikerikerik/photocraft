## Decisions and known gaps

- **Where the limit is checked.** `max_pixels` comes from `GET /v1/tasks`, a network call, so it runs on the job
  worker (first thing, before any pixel is read), not in `run` on the UI thread. The command still fails
  before any pixel is read or encoded; it just fails as a job rather than before the job starts.
- **The provider's limit wins.** When the manager advertises `max_pixels`, that value is used (higher or lower than
  64 MP); 64 MP applies only when nothing is advertised. A manager with no task entry for `fill_masked_area` is
  treated as "not advertised" and the submit then reports the manager's own sentence.
- **"Timeout" in P3** is handled as a poll or result error (the 30 s read timeout surfaces as one). There is no
  overall job deadline; adding one would need a number for slow CPU jobs.
- **Every poll error counts as transient** for the two-in-a-row tolerance (including a 404); retrying twice costs
  about 200 ms.
- **The PC-03 tests leaned on a dropped endpoint file.** `non_rgb_documents_are_refused_before_any_request` and
  `a_request_that_does_not_match_its_window_is_refused` built their provider from a `TempEndpoint` temporary
  that deleted its file at once. The cheap format checks still come before the endpoint read, so the first is
  unchanged; the second now keeps its endpoint alive because its NaN case needs the encoder.
- **X2 on Windows.** The client side is done; whether the early reply survives the reset on Windows depends on
  CAIM's half of X2 (BF-01: `shutdown(Write)` and drain), since Windows discards received data on RST.
- **Upstream code untouched.** All changes are in our files (`ai.rs`, `ai_testing.rs`, `ai_tests.rs`,
  `generative_cmds.rs` and its tests, `crates/ai-client`). `edit_menu_cmds.rs` needed no change: its new-layer
  path already sets alpha = coverage.
- Not done (out of scope): linear EXR data is still sent unconverted (noted in the review, no M1 change); the
  successful-path DELETE (CAIM's 10-minute expiry frees finished jobs).

### Why the X2 tests failed on Windows

`an_early_401_during_a_large_upload_is_reported_as_the_token_message` and
`an_early_error_reply_uses_the_manager_s_sentence` reported "PhotoCraft lost the connection to Craft AI
Manager" instead of the manager's sentence. Measured on the wire: the client's write failed with
`WSAECONNABORTED` (10053) and its later read with `WouldBlock` (10035).

- The fault was in the fake manager, not the client. On Windows a socket from `accept()` inherits the
  listener's non-blocking mode, so the handler's reads failed with `WouldBlock` as soon as the kernel buffer
  emptied: it had drained 25 MB of the announced 30 MB, returned, and closed with about 5 MB unread. Closing
  with unread data sends RST, and Windows throws away data the peer has received but not read, so the
  scripted 401 was gone before the client looked. `serve_one` now puts the socket back to blocking first,
  which is exactly what CAIM's `handle_connection` does for the same reason.
- The fake's early path now models fixed CAIM (BF-01 `close_after_reply`): write the answer, `shutdown(Write)`,
  read and drop the announced body, then close. It drains 29 998 140 of the 29 998 140 bytes announced, the
  upload finishes, and the client reads the scripted reply. Half-closing before draining is fine on Windows
  (this path is the proof); closing with the body unread is not.
- A draining manager never makes the client's write fail, so the write-failure half of X2 is proven by the
  unit test in row 4 rather than end to end. There is no end-to-end test for "manager closes with the body
  unread and the client still reads its answer": the RST takes the answer with it on every platform, which is
  why CAIM's side of X2 (BF-01) drains.
- Flake check: `cargo test -p photocraft-ai-client` ten runs in a row, 39 passed / 0 failed each time.

### Follow-up decisions

- **`AiError::TokenMismatch` is a new engine variant** (the enum is not `#[non_exhaustive]`), so the compiler
  revisited every match on it. The sentence is unchanged, so PC-04's CLI test still passes word for word.
- **The fake manager drains.** `queue_early` no longer closes with the body unread: that is what CAIM does
  after BF-01, and it is the only case where an early answer can survive. The client's fallback (read the
  reply after a failed write, never write again) stays as the other half, proven by the unit test.
- **Not merged here.** The PR still needs an independent review (author: Codex/GPT-6 on Windows for the
  follow-up, reviewer must differ) and a green CI run on both ubuntu and windows.
